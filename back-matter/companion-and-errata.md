Start with the code repository's README, docs/learning-guide.md, docs/milestones.md and docs/verification.md. The milestone record identifies the source appropriate to an earlier chapter. The verification record identifies actual executions and their limits. Current default-branch code can contain later features that were not present in the chapter's first example.

## Retrieve the intended checkpoint

Use a dedicated checkout for an exercise and record its exact revision. Do not replace a working project blindly to match a screenshot. Chapters 1-5 use the recorded Part I starter; later chapters progressively add the interface, persistence, API, identity, media and customer workflows.

A planned chapter or edition tag is not a published checkpoint until it exists and its verification is recorded. This editorial proof cites some later local work that still awaits repository publication. Confirm that a referenced revision is available before treating it as a downloadable milestone. Do not substitute an unrelated newer or older build and retain the original test claim.

## Read an evidence record

Source revision, build configuration, toolchain, package identity and observed environment answer different questions. The Android package candidate and its corrected upgrade harness deliberately retain separate revisions. A synthetic receipt or provider fixture is identified as such. Actual device, live-provider and store checks remain separate rows.

The reference appendices help locate the appropriate boundary. Appendix A revisits C# ownership and lifetime. Appendix B collects environment and diagnostic distinctions. Appendix C maps contracts and configuration. Appendix D describes an optional watch direction without claiming an implemented watch application.

## Report a useful correction

A useful erratum names the chapter/section, manuscript or edition checkpoint, code revision, exact command or short interaction, expected result and observed result. Distinguish a documentation error from a compilation, platform, network, provider or data-recovery failure. Include the first meaningful diagnostic after removing private values.

Use invented information when reproducing a customer workflow. Do not post credentials, private keys, contact stories, private delivery URLs, customer databases or raw diagnostic dumps in a public issue. Follow the repository's current available reporting guidance, particularly for a security-sensitive finding. This book does not promise a particular support response time.

An accepted correction should retain its affected checkpoint, corrected source/instruction, verification and remaining limits. A later correction must not silently rewrite the evidence of an earlier run. See Chapter 40 for the edition and maintenance model.
